# T2. Анализ конвейера «эксперимент → артефакт → страница»

## Постановка

Сравниваются способы, которыми результат вычислений попадает на страницу сайта:

1. статические изображения, сохранённые вручную (базовый вариант);
2. исполнение ноутбука при сборке: `nbconvert`, `MyST-NB`, `Quarto`;
3. `papermill` с параметризацией запуска;
4. отдельный скрипт, генерирующий Markdown и графики, вызываемый из `Makefile` перед сборкой
   (так устроено [P3](p3/index.md)).

## Стенд

Один и тот же расчёт — выход игр по годам и медианная цена по выборке Steam (10 000 игр) —
оформлен как ноутбук и прогнан каждым инструментом. Файлы стенда и команды —
`experiments/t2/` в репозитории.

- macOS, Apple Silicon, Python 3.12;
- nbconvert 7.17.1, nbclient 0.11.0, papermill 2.7.0, MyST-NB 1.4.0 + Sphinx 9.1.0,
  Quarto 1.10.18 (пакет `quarto-cli` из PyPI), jupytext 1.19.5;
- время — стеной, один прогон; «повтор» — второй запуск без изменений.

## Замеры

| Способ | Первый запуск | Повтор без изменений | Данные изменились, код нет | Результат |
|---|---|---|---|---|
| Ручные изображения | 0 с (расчёт вне сборки) | 0 с | страница не меняется, пока человек не пересохранит картинку | PNG в репозитории |
| nbconvert `--execute` | 2,23 с (самый первый — 15,84 с) | 1,98 с | пересчитывает всегда, кэша нет | Markdown 4 КБ + PNG 12 КБ |
| papermill | 1,74 с | 1,73 с | пересчитывает всегда, кэша нет | ноутбук с выводами 24 КБ |
| MyST-NB, `nb_execution_mode = "cache"` | 4,97 с | 1,22 с | **показывает старый результат** | сайт Sphinx 332 КБ, страница 8 КБ |
| Quarto, `freeze: auto` | 2,87 с | 1,02 с | **показывает старый результат** | сайт 1196 КБ, страница 24 КБ |
| Скрипт + `Makefile` (P3) | 0,48 с локально, 2,25–6,13 с в CI | 0,001 с локально, 0,002 с в CI | пересчитывает: данные входят в ключ кэша | Markdown + 2 PNG, страница P3 64 КБ |

Самый первый запуск nbconvert занял 15,84 с против 2,23 с у следующего: при первом импорте
matplotlib строит кэш шрифтов, а Jupyter регистрирует ядро. На чистом CI-раннере эта цена
платится в каждом запуске, если кэш `~/.cache/matplotlib` не сохранять.

### Кэш ноутбуков не видит данных

Проверка: после первой сборки в `data.csv` оставлены первые 2000 строк (MyST-NB) и 1000 строк
(Quarto), затем сборка повторена.

| Инструмент | В `data.csv` строк | На странице |
|---|---|---|
| MyST-NB | 2000 | `Игр: 10000, медианная цена: 3.99` |
| Quarto | 1000 | `Игр: 10000, медианная цена: 3.99` |

Оба инструмента строят ключ кэша по коду ячеек, а файлы, которые код читает, в ключ не входят.
Изменение данных без изменения кода даёт страницу со старыми числами и без ошибки сборки.
Обход — сбрасывать кэш при изменении данных (`hashFiles('data/**')` в ключе кэша CI) или
принудительное исполнение (`quarto render --execute`, `nb_execution_mode = "force"`),
которое отменяет выигрыш от кэша.

## Сравнение

| Критерий | Ручные изображения | nbconvert | papermill | MyST-NB | Quarto | Скрипт + Makefile |
|---|---|---|---|---|---|---|
| Исполнение при сборке | нет | да | да | да | да | да |
| Параметры запуска | — | нет | **да**, `-p name value` | нет | да, `params` в `.qmd` | аргументы скрипта |
| Кэш результатов | — | нет | нет | по коду ячеек | по коду (`_freeze/`) | по хешу данных, кода и `uv.lock` |
| Нужно ядро Jupyter в CI | нет | да | да | да | да | нет |
| Связь с MkDocs | вручную | вывод Markdown | нет, нужен nbconvert | только Sphinx | свой генератор | Markdown в `docs/` |
| Ошибка в расчёте ломает сборку | нет | да | да | настраивается | да | да |
| Воспроизводимость | нет: неизвестно, каким кодом получено | да | да, параметры записаны в ноутбук | да | да | да |

Выводы из таблиц:

- Ручные изображения — единственный способ, при котором страница может разойтись с кодом
  без каких-либо сигналов.
- papermill — единственный с параметризацией из коробки и записью параметров в выходной
  ноутбук; своего кэша и вывода под сайт у него нет, он стоит перед nbconvert.
- MyST-NB и Quarto дают кэш «из коробки», но только по коду; для экспериментов, где меняются
  данные, это ловушка из раздела выше.
- Скрипт с явным ключом кэша требует больше ручного кода, но единственный из сравниваемых
  пересчитывает результат при смене данных и не требует Jupyter в CI.

## Ограничения CI для тяжёлых вычислений

По документации GitHub Actions (стандартные раннеры):

| Ограничение | Значение | Источник |
|---|---|---|
| Время одного job | 6 ч | [Actions limits](https://docs.github.com/en/actions/reference/limits) |
| Время workflow run | 35 дней | там же |
| Параллельные job, план Free | 20 | там же |
| Минуты | публичный репозиторий — без ограничений; приватный на Free — 2000 мин/мес | [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [Billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) |
| Ресурсы Linux-раннера | публичный: 4 CPU, 16 ГБ RAM, 14 ГБ SSD; приватный: 2 CPU, 8 ГБ RAM, 14 ГБ SSD | [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) |
| GPU | на стандартных раннерах нет; только larger runners на планах Team и Enterprise Cloud | там же |
| Кэш | 10 ГБ на репозиторий, удаляется через 7 дней без обращений, при переполнении вытесняются самые старые; кэш ветки недоступен из `main` | [Dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [Actions limits](https://docs.github.com/en/actions/reference/limits) |
| Хранилище артефактов, план Free | 500 МБ | [Billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) |

Следствия для публикации результатов:

- кэш нельзя считать хранилищем результатов: через 7 дней простоя он исчезает, и следующая
  сборка платит полный пересчёт;
- данные больше ~10 ГБ не помещаются ни в диск раннера с учётом окружения, ни в кэш;
- обучение моделей и расчёты на GPU в стандартном CI невозможны.

## Граница между стратегиями

**Вычисления выполняются в CI**, если одновременно:

- расчёт укладывается в минуты, а не часы, на 2–4 CPU без GPU;
- входные данные — до сотен мегабайт и лежат в репозитории или публичном источнике;
- расчёт детерминирован: повтор на том же входе даёт тот же результат;
- для расчёта не нужны секреты, кроме тех, что уже в хранилище секретов.

Так устроен P3: расчёт по 10 000 строк — 2–6 с на раннере.

**Вычисления выполняются отдельно, CI собирает сайт из готовых артефактов**, если нарушено
хотя бы одно из условий: часы расчёта, GPU, данные в гигабайтах, закрытые данные,
стохастические методы, которые нельзя повторять при каждой сборке.

## Связь результата с версией кода и данных во второй стратегии

Готовый артефакт сопровождается манифестом, который пишет сам расчёт:

```json
{
  "code_commit": "30c959b",
  "dataset": {"name": "Kaggle Steam Games", "version": 62, "sha256": "0172fa22ef62..."},
  "params": {"min_year": 2020, "seed": 43},
  "env_lock_sha256": "bb26ec577d41...",
  "started_at": "2026-09-26T17:05:00Z",
  "host": "gpu-node-1",
  "outputs": {"releases_by_year.png": "sha256:..."}
}
```

Правила:

1. Артефакты и манифест хранятся вне git: релиз GitHub, объектное хранилище или DVC.
   В репозиторий попадает только ссылка и хеши.
2. CI при сборке скачивает артефакт, сверяет хеши файлов с манифестом и проверяет, что
   `code_commit` есть в истории; при несовпадении сборка падает.
3. На странице выводится метка из манифеста — коммит кода, версия датасета, параметры,
   дата расчёта — отдельно от даты сборки сайта. В P3 такая метка собирается хуком
   `hooks/build_info.py`.
4. Повторный расчёт с тем же кодом, данными и параметрами должен давать те же хеши;
   расхождение — сигнал недетерминированности.
